# Permission rule scripts

## Generated curl and aws rules

The curl write-flag asks (every prefix, every bundled-short-flag width) and the
aws read-only allows (per service) in
`extensions/pi-permission-system/config.json` are generated, not hand-edited.
The spec and generator live in `permission-rules.mjs`.

1. Edit the `spec` object at the top of `permission-rules.mjs`
   (curl prefixes, flags, `bundleWidth`; aws `services`, `readVerbs`).
2. Regenerate: `node pi/.pi/agent/scripts/permission-rules.mjs`.
   Each block is located by the hand-edited rules directly before and after it
   in config.json (`neighbors` in the spec, outside the generated set); every
   rule between them is replaced and all other rules keep their position. The
   generator throws, without writing, if a neighbor is missing, duplicated or
   out of order, or if a generated rule would duplicate one outside the block.
   If you rename or move a neighbor rule in config.json, update `neighbors`.
   The generator records the keys it wrote, per block and in order, in
   `permission-rules.lock.json` next to the spec (commit it). Before anything
   is written, every rule between a block's neighbors must be listed in that
   block's manifest entry or generated by the current spec; otherwise the tool
   throws, names every offending key and writes nothing. Hand-written rules inside a span are never deleted,
   even if they look generated (`curl * -o*: ask`): the tool refuses instead.
   This also catches a moved neighbor (which would otherwise drop the rules in
   between). Hand-written rules must go outside the neighbor span. Manifest
   keys missing from config.json (deleted by hand) are fine and are reported
   as a note, unless the spec no longer generates them. A key the spec
   generates that is not in the manifest (a stale manifest) is replaced only
   if its current value already equals the generated value; a hand-written
   rule with a different value makes the tool throw, naming the key with both
   values, and write nothing (overwriting could silently loosen a deny). Any spec change (prefixes, flags, `action`, `pipeDenyRule`,
   aws `leadingAllows`, `services`, `readVerbs`) regenerates cleanly.
   After a successful write the manifest is rewritten to the new generated
   keys. config.json is written first, then the manifest, each via a temp file
   in the same directory renamed into place; config.json's mode is preserved
   and a symlink is written through to its target. If the manifest is missing
   it is created from the current spec only when config.json already matches
   the spec; otherwise the tool throws (fix config.json by hand to match the
   spec first). A stale manifest (for example after a crash between the two
   renames) is not an error: a normal run repairs it, and `--check` reports it
   and exits 1. The tool also throws if the two spans overlap, if
   `permission.bash` is missing or not an object, if the file is not valid
   JSON, or if a bash key is integer-like (JSON objects reorder those). CLI
   errors print one line and exit non-zero; unknown flags and a missing or
   flag-like `--config`/`--manifest` value are rejected. `--config <path>` targets another
   file, with the manifest next to it (or `--manifest <path>`); the tests use
   this.
3. Check config.json is in sync: `node pi/.pi/agent/scripts/permission-rules.mjs --check`
   (exit 1 if config.json or the manifest differs from the spec).
4. Run the tests: `node --test pi/.pi/agent/scripts/permission-rules.test.mjs`.
5. Run the replay check:
   `node pi/.pi/agent/scripts/permission-replay.mjs pi/.pi/agent/scripts/baseline-config.json pi/.pi/agent/extensions/pi-permission-system/config.json`

Rules outside the blocks (e.g. `curl * | bash`, the aws `ask`/`deny` rules)
remain hand-edited in config.json.
